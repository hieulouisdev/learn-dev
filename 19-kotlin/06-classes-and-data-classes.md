# Lesson 06: Classes and Data Classes

> Module: Kotlin · Lesson 6 of 7
> Estimated time: 45–60 minutes

This is the longest lesson in the module because classes are the heart of Kotlin's object-oriented side, and Kotlin introduces several features that Java developers envy: properties declared in the constructor, the `data class` keyword that auto-generates `equals`/`hashCode`/`toString`/`copy`, sealed classes for restricted hierarchies (Rust-style enums), `object` declarations for singletons in one line, and `companion object` for static-like members. By the end of this lesson you will understand why `data class User(val name: String, val age: Int)` replaces 30+ lines of Java boilerplate.

You do not need to know Java's class system to read this lesson, but if you do, you will spend most of the lesson noticing how much boilerplate Kotlin eliminates. Classes in Kotlin are concise by design — the primary constructor lives in the class header, properties are declared in the constructor parameters, and common methods are auto-generated by the compiler when you mark a class as `data`.

---

## Learning Objectives

After this lesson, you will be able to:

1. Declare a class with a primary constructor and properties in one line: `class Person(val name: String, val age: Int)`.
2. Use `open`, `override`, and `interface` correctly, and explain why Kotlin classes are `final` by default.
3. Use `data class` to auto-generate `equals`, `hashCode`, `toString`, `copy`, and destructuring components, and explain when to use it vs a regular class.
4. Use `sealed class` with `when` for exhaustive pattern matching, and use `object` and `companion object` for singletons and static-like members.

## 1. Defining a Class

Kotlin's class syntax is dramatically more concise than Java's. A class with two properties — name and age — is one line:

```kotlin
class Person(val name: String, val age: Int)

fun main() {
    val p = Person("Hieu", 25)
    println(p.name)  // Hieu
    println(p.age)   // 25
    println(p)        // Person@1b6d3586 (default toString, not very useful)
}
```

- `class Person(val name: String, val age: Int)` — declares a class named `Person` with a **primary constructor** that takes two parameters. The `val` keyword before each parameter turns it into a **property** of the class — the compiler auto-generates a getter (read-only, because `val`). With `var`, it would also generate a setter.
- `Person("Hieu", 25)` — constructs an instance. There is no `new` keyword in Kotlin — you call the constructor like a regular function.
- `p.name`, `p.age` — access the properties. Kotlin promotes properties to first-class — you write `p.name` (no parentheses) and the compiler calls the getter under the hood. If the property is `var`, assignment like `p.age = 26` calls the setter.

Compare this to Java, where the same class needs a constructor, two private fields, two getters, and probably `equals`/`hashCode`/`toString` overrides — easily 30 lines of code. Kotlin collapses it into one line.

### Classes with Bodies

If you need to add methods, secondary constructors, or `init` blocks, add a body in braces:

```kotlin
class Person(val name: String, val age: Int) {
    // Property declared in the body
    var email: String? = null

    // init block runs during construction
    init {
        println("Created $name, age $age")
    }

    // Method
    fun greet(): String = "Hi, I'm $name"

    // Property with a custom getter
    val isAdult: Boolean
        get() = age >= 18
}

fun main() {
    val p = Person("Hieu", 25)
    p.email = "hieu@example.com"
    println(p.greet())     // Hi, I'm Hieu
    println(p.isAdult)     // true
}
```

- `var email: String? = null` — a mutable property declared in the body, initialized to `null`. Defaults can be assigned at declaration.
- `init { ... }` — an **init block** that runs during object construction. You can have multiple `init` blocks; they run in the order they appear in the class body, after the primary constructor's property initializers.
- `fun greet(): String = "Hi, I'm $name"` — a method. Methods are functions declared inside the class body.
- `val isAdult: Boolean get() = age >= 18` — a property with a **custom getter**. The property has no backing field; its value is computed each time it is read. Note `get()` instead of `=` for the property initializer.

## 2. Properties — Fields ARE Properties

In Java, you write a private field and then a getter and setter method (`getName`, `setName`). In Kotlin, fields and properties are unified — every `val`/`var` declaration IS a property, with the getter (and setter) auto-generated.

```kotlin
class Temperature(var celsius: Double) {
    // Derived property — computed from celsius
    val fahrenheit: Double
        get() = celsius * 9 / 5 + 32

    // Setter for a property — runs when you assign
    var kelvin: Double
        get() = celsius + 273.15
        set(value) {
            celsius = value - 273.15
        }
}

fun main() {
    val t = Temperature(25.0)
    println(t.fahrenheit)  // 77.0 — calls the getter
    t.kelvin = 300.0       // calls the setter
    println(t.celsius)     // 26.85
}
```

- `var celsius: Double` — a mutable property. Auto-generates `getCelsius()` and `setCelsius()` under the hood (visible if you call the class from Java).
- `val fahrenheit: Double get() = ...` — a derived property with a custom getter. No backing field; the value is computed on each access.
- `var kelvin: Double get() = ... set(value) { ... }` — a property with both a custom getter AND a custom setter. The `set(value)` syntax defines the setter; `value` is the new value being assigned.

Kotlin's unified property model means you never write `getX()`/`setX()` boilerplate. Just declare `val` or `var` and you get the accessors automatically. You can override them with custom `get()`/`set()` blocks when you need custom logic, without changing the call site — `t.kelvin = 300.0` looks identical whether `kelvin` is a stored property or a computed one.

## 3. Constructors — Primary and Secondary

Kotlin distinguishes the **primary constructor** (declared in the class header) from **secondary constructors** (declared with `constructor(...)` inside the body). The primary is preferred for most cases.

```kotlin
// Primary constructor with type annotations
class User(val name: String, val age: Int)

// Primary constructor with defaults
class Settings(
    val theme: String = "light",
    val fontSize: Int = 14,
    val notifications: Boolean = true
)

// Primary constructor without properties (just initialization parameters)
class Logger(private val tag: String) {
    fun log(message: String) = println("[$tag] $message")
}

// Secondary constructor — delegates to primary
class Person(val name: String) {
    var age: Int = 0

    constructor(name: String, age: Int) : this(name) {
        this.age = age
    }
}

fun main() {
    val u = User("Hieu", 25)
    val s = Settings(theme = "dark")
    val log = Logger("APP")
    log.log("Started")

    val p1 = Person("Alice")
    val p2 = Person("Bob", 30)
    println("${p1.name}, ${p1.age}")  // Alice, 0
    println("${p2.name}, ${p2.age}")  // Bob, 30
}
```

- `class User(val name: String, val age: Int)` — primary constructor in the class header. Each `val`/`var` parameter becomes a property.
- `class Settings(val theme: String = "light", ...)` — primary constructor with **default arguments**. Callers can omit any subset: `Settings(theme = "dark")` keeps the other defaults.
- `class Logger(private val tag: String)` — the `private` modifier on a constructor parameter makes the property accessible only inside the class (not from outside). Without `private`, properties are `public` by default.
- `constructor(name: String, age: Int) : this(name) { ... }` — a **secondary constructor**. Secondary constructors are declared with the `constructor` keyword. They must delegate to the primary constructor via `: this(...)`. The body runs after the primary constructor.
- Secondary constructors are uncommon in idiomatic Kotlin. Most cases are better expressed with default arguments on the primary constructor. Use secondary constructors only when you genuinely need different parameter lists that cannot be expressed as defaults.

### `init` Blocks

The `init` block is where you put setup logic that needs to run during construction. It runs after the primary constructor's property initializers but before secondary constructor bodies:

```kotlin
class Account(val owner: String, initialBalance: Int) {
    val balance: Int

    init {
        require(initialBalance >= 0) { "Balance cannot be negative" }
        balance = initialBalance
        println("Account opened for $owner with $balance")
    }
}

fun main() {
    val acc = Account("Hieu", 100)  // Account opened for Hieu with 100
    // Account("Bob", -50)  // Throws IllegalArgumentException
}
```

- `require(initialBalance >= 0) { ... }` — `require` is a standard-library function that throws `IllegalArgumentException` with the given message if the condition is false. Common in `init` blocks for validating constructor arguments.
- `init { ... }` — runs after `owner` and `balance` are initialized. You can have multiple `init` blocks; they run in source-code order.

Note that `initialBalance` is a plain constructor parameter (not `val`/`var`), so it is not a property — it is only available inside the `init` block and constructor body. Use this for values you need during construction but not as part of the object's state.

## 4. Visibility Modifiers

Kotlin has four visibility modifiers:

```kotlin
// public — visible everywhere (default)
class PublicClass {
    public val x = 1
}

// private — visible inside the same file (top-level) or same class (member)
class PrivateExample {
    private val secret = "hidden"

    fun reveal() = secret  // OK — inside the class
}

// internal — visible inside the same module (a set of compiled files)
class InternalExample {
    internal val moduleOnly = "module"
}

// protected — visible inside the class and its subclasses (members only)
open class Parent {
    protected val familySecret = "shh"
}

class Child : Parent() {
    fun reveal() = familySecret  // OK — Child inherits Parent
}

fun main() {
    // PublicExample().x         // OK — public
    // PrivateExample().secret   // ERROR — private
}
```

- `public` — visible everywhere. **This is the default** if you do not specify anything. Kotlin's default is the opposite of Java's (where the default is package-private).
- `private` — for top-level declarations (functions, classes, properties outside a class), visible inside the same source file. For class members, visible only inside the class.
- `internal` — visible inside the same **module** (a compiled unit, typically a Gradle module or Maven artifact). Useful for APIs that should be accessible within a library but hidden from its consumers. There is no equivalent in Java.
- `protected` — for class members only, visible inside the class and its subclasses. Cannot be used on top-level declarations.

Kotlin does not have Java's package-private visibility. If you want something accessible across files within the same module, use `internal`. If you want it limited to one file, use `private`.

## 5. Inheritance — `open` and `override`

Kotlin classes are **final by default** — they cannot be inherited from. To allow subclassing, you must explicitly mark the class as `open`. This is the opposite of Java, where classes are open by default and you must opt out with `final`.

```kotlin
// Final class — cannot be subclassed
class FinalClass

// Open class — can be subclassed
open class Animal(val name: String) {
    // Open method — can be overridden
    open fun speak(): String = "$name makes a sound"

    // Non-open method — cannot be overridden
    fun description(): String = "Animal named $name"
}

class Dog(name: String) : Animal(name) {
    override fun speak(): String = "$name says Woof!"
}

class Cat(name: String) : Animal(name) {
    override fun speak(): String = "$name says Meow!"
}

fun main() {
    val a: Animal = Dog("Rex")
    println(a.speak())  // Rex says Woof! — dynamic dispatch

    val c = Cat("Whiskers")
    println(c.speak())  // Whiskers says Meow!
}
```

- `open class Animal(...)` — the `open` keyword on the class declaration allows it to be subclassed. Without `open`, attempting to inherit from it is a compile error.
- `class Dog(name: String) : Animal(name)` — `Dog` inherits from `Animal`. The `: Animal(name)` syntax calls the parent's constructor with the given argument. Kotlin uses `:` instead of Java's `extends` keyword.
- `open fun speak()` — methods are also final by default. The `open` keyword on a method allows it to be overridden.
- `override fun speak(): String` — the `override` keyword marks a method as overriding a parent's method. `override` is MANDATORY in Kotlin — without it, you would shadow the parent method (which Kotlin forbids by default, with a compile-time warning or error).
- `val a: Animal = Dog("Rex")` — `a` has the static type `Animal` but holds a `Dog` instance. Calling `a.speak()` dispatches dynamically to `Dog.speak()` — this is runtime polymorphism, the same as in Java.

The `open` by default principle prevents accidental inheritance, which is a common source of bugs in Java. The Kotlin team's view: if you want a class to be inheritable, mark it `open` — this is a deliberate design decision, not the default. Most classes are not designed for inheritance and should be final.

## 6. Interfaces

Interfaces in Kotlin are similar to Java's — they declare methods that implementing classes must provide. Interfaces can have default implementations, and a class can implement multiple interfaces.

```kotlin
interface Greeter {
    fun greet(): String

    // Default implementation
    fun politeGreet(): String = "Good day! ${greet()}"
}

interface Speaker {
    fun speak(volume: Int): String
}

// Implement multiple interfaces
class Friendly : Greeter, Speaker {
    override fun greet(): String = "Hi!"

    override fun speak(volume: Int): String =
        if (volume > 5) "HELLO!" else "hello"
}

fun main() {
    val f = Friendly()
    println(f.greet())           // Hi!
    println(f.politeGreet())     // Good day! Hi!  (uses default)
    println(f.speak(3))          // hello
    println(f.speak(10))         // HELLO!
}
```

- `interface Greeter { ... }` — declares an interface.
- `fun greet(): String` — a method without a body. Implementing classes must provide a body.
- `fun politeGreet(): String = "Good day! ${greet()}"` — a method WITH a default body. Implementing classes can use the default or override it.
- `class Friendly : Greeter, Speaker` — implements both interfaces, separated by commas. (Note: a class can extend at most ONE base class but implement MANY interfaces — same as Java.)
- `override fun greet(): String = "Hi!"` — implements the required method.
- `f.politeGreet()` — uses the default implementation from the interface, which calls `f.greet()` (overridden in `Friendly`). The default method calls the abstract one — common pattern.

Interfaces can also have properties (abstract, or with a getter defined):

```kotlin
interface Named {
    val name: String
    val upperName: String get() = name.uppercase()
}

class User(override val name: String) : Named

fun main() {
    val u = User("hieu")
    println(u.name)       // hieu
    println(u.upperName)  // HIEU
}
```

## 7. Data Classes — The Most-Loved Feature

The `data class` keyword is the most-loved feature in Kotlin. It tells the compiler to auto-generate `equals`, `hashCode`, `toString`, `copy`, and `componentN` (for destructuring) based on the properties in the primary constructor:

```kotlin
data class User(val name: String, val age: Int)

fun main() {
    val u1 = User("Hieu", 25)
    val u2 = User("Hieu", 25)
    val u3 = User("Bob", 30)

    // Auto-generated toString
    println(u1)  // User(name=Hieu, age=25)

    // Auto-generated equals (structural, based on properties)
    println(u1 == u2)  // true — same property values
    println(u1 == u3)  // false

    // Auto-generated copy — creates a new instance with some properties changed
    val olderU1 = u1.copy(age = 26)
    println(olderU1)  // User(name=Hieu, age=26)
    println(u1)        // User(name=Hieu, age=25) — original unchanged

    // Auto-generated componentN — enables destructuring
    val (name, age) = u1
    println("Name: $name, Age: $age")  // Name: Hieu, Age: 25
}
```

- `data class User(val name: String, val age: Int)` — the `data` modifier tells the compiler to generate the standard methods.
- `u1 == u2` returns `true` because `equals` compares property values, not references. Without `data`, `==` would still call `.equals()`, but the default `Any.equals()` compares references.
- `u1.copy(age = 26)` — creates a NEW `User` with the same `name` but `age` changed to `26`. The original `u1` is unchanged. This is the idiomatic way to "modify" a `data class` — since they are usually immutable (`val` properties).
- `val (name, age) = u1` — **destructuring declaration**. The compiler auto-generates `component1()` (returns `name`) and `component2()` (returns `age`). The syntax `val (a, b) = x` calls `x.component1()` and `x.component2()`. Works for up to 5 components by default; for more, declare your own `operator fun componentN()`.

### When to Use `data class` vs Regular `class`

Use `data class` for:
- DTOs (Data Transfer Objects) — value holders passed between layers
- Domain model entities with mostly `val` properties (immutable)
- Anything where you naturally want `equals`/`hashCode`/`toString` based on the properties

Use a regular `class` for:
- Objects with mutable state and behavior (like a service or controller)
- Classes that should NOT have value-based `equals` (e.g., a database connection — you want identity equality)
- Classes whose identity is more important than their state

### Requirements for `data class`

A `data class` has a few rules:
1. The primary constructor must have at least one parameter.
2. All primary constructor parameters must be `val` or `var` (properties).
3. `data class` cannot be `open`, `abstract`, `sealed`, or `inner`.

```kotlin
// Valid data class
data class Point(val x: Double, val y: Double)

// INVALID — would not compile
// data class Empty          // no parameters
// open data class Foo(val x: Int)  // cannot be open
```

## 8. Sealed Classes — Restricted Hierarchies

A **sealed class** is a class that can only be subclassed inside the same file (or, since Kotlin 1.5, the same package and module). This lets the compiler know ALL possible subclasses at compile time, which enables **exhaustive pattern matching** in `when` expressions. Sealed classes are Kotlin's equivalent of Rust's enums or Swift's enums with associated values.

```kotlin
sealed class Result {
    data class Success(val value: String) : Result()
    data class Error(val message: String) : Result()
    object Loading : Result()
}

fun handle(result: Result): String = when (result) {
    is Result.Success -> "Got: ${result.value}"
    is Result.Error    -> "Failed: ${result.message}"
    Result.Loading     -> "Loading..."
}

fun main() {
    val r1: Result = Result.Success("OK")
    val r2: Result = Result.Error("Not found")
    val r3: Result = Result.Loading

    println(handle(r1))  // Got: OK
    println(handle(r2))  // Failed: Not found
    println(handle(r3))  // Loading...
}
```

- `sealed class Result { ... }` — declares a sealed class. All direct subclasses must be declared in the same file (Kotlin 1.5+: same package/module).
- `data class Success(val value: String) : Result()` — a nested data class that extends `Result`. Each subclass can have its own properties.
- `object Loading : Result()` — a singleton object that extends `Result`. Used for the "no data" case.
- `when (result) { is Result.Success -> ...; is Result.Error -> ...; Result.Loading -> ... }` — exhaustive pattern matching. The compiler KNOWS there are exactly three subclasses, so if you forget one, it errors with `'when' expression must be exhaustive`. Note: no `else` branch needed because all cases are covered.

### Why Sealed Classes Are Powerful

Sealed classes give you the safety of an enum (restricted number of cases) with the flexibility of a class hierarchy (each case can have different properties). They are perfect for modeling:

- **API responses**: `Success(data)`, `Error(message, code)`, `Loading`
- **State machines**: `Idle`, `Loading`, `Loaded(data)`, `Failed(error)`
- **AST nodes**: `Number(value)`, `String(value)`, `BinaryOp(op, left, right)`, `FunctionCall(name, args)`
- **Result types**: `Ok(value)`, `Err(error)` — like Rust's `Result`

If you ever modeled these with Java class hierarchies and forgot a case in a `switch`/`if` chain, you will appreciate the compile-time guarantee that sealed classes provide.

## 9. Object Declarations — Singletons

Kotlin's `object` keyword declares a **singleton** in a single line — a class that has exactly one instance. The instance is created lazily on first access, and there is no constructor (you cannot create more instances).

```kotlin
object Database {
    private val connection = connect()

    fun query(sql: String): List<String> {
        println("Executing: $sql")
        return listOf("row1", "row2")
    }

    fun close() {
        println("Closing connection")
    }
}

fun main() {
    Database.query("SELECT * FROM users")  // Executing: SELECT * FROM users
    Database.query("SELECT * FROM orders")  // Executing: SELECT * FROM orders
    Database.close()                        // Closing connection
}

// Helper to "connect"
fun connect(): Any = "fake-connection"
```

- `object Database { ... }` — declares a singleton object named `Database`. There is exactly one instance for the lifetime of the program.
- `Database.query(...)` — access the singleton directly via its name, no instantiation. Like calling a static method in Java.
- `private val connection = connect()` — initialized lazily when the singleton is first accessed. The first call to `Database.query(...)` triggers initialization.

In Java, you would write a class with a private constructor and a static `INSTANCE` field — about 10 lines of boilerplate. In Kotlin, `object` collapses it to one keyword. Use `object` for things like configuration registries, logger instances, cache singletons, or any "global service" that should have exactly one instance.

### Object Expressions (Anonymous Objects)

A related feature is the **object expression** — creating an anonymous object that implements an interface or extends a class, on the fly:

```kotlin
interface ClickListener {
    fun onClick(): Unit
}

fun main() {
    val listener = object : ClickListener {
        override fun onClick() = println("Clicked!")
    }
    listener.onClick()  // Clicked!
}
```

This is Kotlin's equivalent of Java's anonymous classes (`new ClickListener() { ... }`). Useful for passing one-off implementations as arguments without declaring a named class.

## 10. Companion Objects — Static-Like Members

Kotlin does not have Java's `static` keyword. Instead, you put static-like members inside a **companion object** — a singleton object nested inside a class, whose members can be accessed via the class name:

```kotlin
class User(val name: String, val age: Int) {
    companion object {
        // Constants
        const val MIN_AGE = 0
        const val MAX_AGE = 150

        // Factory method
        fun create(name: String): User = User(name, 0)

        // Counter for instances created
        private var instancesCreated = 0
        fun totalCreated(): Int = instancesCreated
    }

    init {
        // Cannot easily access companion from instance init
    }
}

fun main() {
    println(User.MIN_AGE)             // 0 — accessed via class name
    println(User.MAX_AGE)            // 150

    val u = User.create("Anonymous")  // factory method
    println(u.name)                    // Anonymous
}
```

- `companion object { ... }` — declares a companion object inside the class. The companion's members are accessed via the class name (`User.MIN_AGE`, `User.create(...)`), like static members in Java.
- `const val MIN_AGE = 0` — `const` marks a compile-time constant. Must be a primitive or `String`. The value is inlined at every use site.
- `fun create(name: String): User = User(name, 0)` — a **factory method**. Use this pattern when you want a more readable way to construct instances than the regular constructor, or when you want to return a subtype.
- `private var instancesCreated = 0` — companion objects can hold state, shared across all instances of the class.

### Why Companion Object Instead of `static`?

Kotlin's design avoids `static` because static members cannot be overridden (no polymorphism), cannot implement interfaces, and make testing harder. A `companion object` is a real object — it can implement interfaces, be passed as a parameter, and (with some effort) be mocked in tests. The Kotlin team's view: when you need static-like behavior, the explicit `companion object` makes it clear what you are doing, and you can choose a more flexible pattern when you need it.

## 11. Putting It All Together

Here is a moderately realistic example combining many features from this lesson:

```kotlin
// Sealed class for state
sealed class UiState {
    object Loading : UiState()
    data class Success(val items: List<String>) : UiState()
    data class Error(val message: String) : UiState()
}

// Data class for the model
data class Todo(val id: Int, val title: String, val done: Boolean = false)

// Open class with inheritance
open class Repository {
    protected val items = mutableListOf<Todo>()

    open fun all(): List<Todo> = items.toList()

    fun add(todo: Todo) {
        items.add(todo)
    }
}

// Subclass with additional behavior
class TodoRepository : Repository() {
    fun toggle(id: Int) {
        val idx = items.indexOfFirst { it.id == id }
        if (idx >= 0) {
            items[idx] = items[idx].copy(done = !items[idx].done)
        }
    }
}

// Singleton object
object StateManager {
    fun render(state: UiState): String = when (state) {
        UiState.Loading        -> "Loading..."
        is UiState.Success     -> "Items: ${state.items.joinToString { it }}"
        is UiState.Error       -> "Error: ${state.message}"
    }
}

fun main() {
    val repo = TodoRepository()
    repo.add(Todo(1, "Learn Kotlin"))
    repo.add(Todo(2, "Build app", done = true))

    println(StateManager.render(UiState.Loading))
    // Loading...

    println(StateManager.render(UiState.Success(repo.all().map { it.title })))
    // Items: Learn Kotlin, Build app

    repo.toggle(1)
    println(repo.all())
    // [Todo(id=1, title=Learn Kotlin, done=true), Todo(id=2, title=Build app, done=true)]
}
```

This example combines: a `sealed class` (`UiState`), `data class` (`Todo`), `open class` and `override` (`Repository`/`TodoRepository`), `object` singleton (`StateManager`), default arguments (`done = false`), and exhaustive `when` matching. This is what idiomatic Kotlin looks like in real codebases.

## Try It Yourself

Before moving on, do these three exercises. They should take 10–15 minutes each.

### Exercise 1: Define a Data Class

Define a `data class Book(val title: String, val author: String, val year: Int, val pages: Int)`. Create three instances with the same title and author but different years and pages. Then:
1. Print one (notice the auto-generated `toString` shows all properties).
2. Use `copy(year = 2024)` to create a new instance with a different year.
3. Compare two instances with `==` (notice that the comparison is based on property values, not references).
4. Destructure one instance with `val (title, author, year, pages) = book` and print each component.

### Exercise 2: Sealed Class for Payment Method

Define a sealed class `PaymentMethod` with three subclasses: `data class CreditCard(val number: String, val cvv: String)`, `data class PayPal(val email: String)`, and `object Cash`. Write a function `fun describe(p: PaymentMethod): String` that uses `when` to return a description for each. Notice that no `else` branch is needed — the compiler knows the three cases are exhaustive. Try adding a fourth subclass (`data class Crypto(val wallet: String)`) and observe that the compiler warns you that the `when` is no longer exhaustive — forcing you to handle the new case.

## Common Mistakes

### Mistake 1: Trying to inherit from a non-`open` class

```kotlin
// WRONG — Animal is final by default, cannot be subclassed
class Animal(val name: String)

class Dog(name: String) : Animal(name)  // COMPILE ERROR: This type is final, so it cannot be inherited from
```

```kotlin
// RIGHT — mark the parent class as open
open class Animal(val name: String)

class Dog(name: String) : Animal(name)
```

Kotlin classes are `final` by default — they cannot be subclassed. To allow subclassing, you must explicitly mark the class as `open`. This is the opposite of Java, where classes are open by default and you opt out with `final`. The Kotlin team's reasoning: inheritance should be a deliberate design decision, not the default. If you forget `open` and try to inherit from a final class, the compiler stops with `This type is final, so it cannot be inherited from`. The fix is to add `open` to the parent class declaration. The same rule applies to methods — they are final by default, and you must mark them `open` to allow `override`.

### Mistake 2: Forgetting `override` keyword

```kotlin
// WRONG — missing override keyword
open class Animal {
    open fun speak() = "..."
}

class Dog : Animal() {
    fun speak() = "Woof"  // COMPILE ERROR: 'speak' hides member of supertype and needs override
}
```

```kotlin
// RIGHT — use override keyword
open class Animal {
    open fun speak() = "..."
}

class Dog : Animal() {
    override fun speak() = "Woof"
}
```

In Java, `@Override` is optional (it is a hint to the compiler). In Kotlin, the `override` keyword is MANDATORY — without it, the compiler refuses to compile and tells you that your method "hides member of supertype and needs `override` modifier". This prevents a common Java bug: a parent class adds a method with the same name as one of your existing methods, and you accidentally override it without realizing. By requiring `override` explicitly, Kotlin makes intent unambiguous. If you forget, just add the `override` keyword.

### Mistake 3: Expecting `==` to call `.equals()` for arrays (it doesn't)

```kotlin
// WRONG — == on arrays compares references, not contents
fun main() {
    val a = arrayOf(1, 2, 3)
    val b = arrayOf(1, 2, 3)
    println(a == b)  // false! (arrays use reference equality)
}
```

```kotlin
// RIGHT — use .contentEquals() to compare array contents
fun main() {
    val a = arrayOf(1, 2, 3)
    val b = arrayOf(1, 2, 3)
    println(a.contentEquals(b))  // true

    // Or prefer List<Int>, where == works as expected
    val x = listOf(1, 2, 3)
    val y = listOf(1, 2, 3)
    println(x == y)  // true
}
```

In Kotlin, `==` calls `.equals()` for most types — but arrays are an exception. Arrays in Kotlin (like `Array<Int>`, `IntArray`) inherit Java's reference-based `equals`, so `arrayOf(1,2,3) == arrayOf(1,2,3)` returns `false` because they are different objects. To compare contents, use the `.contentEquals()` extension function. Better yet, prefer `List<T>` (via `listOf(...)`) where `==` does structural comparison correctly. This is a quirk inherited from Java for backward compatibility.

### Mistake 4: Using `data class` for mutable state

```kotlin
// UNIDIOMATIC — using var in a data class defeats its purpose
data class Counter(var count: Int)

fun main() {
    val c1 = Counter(5)
    val c2 = c1.copy()
    c1.count++
    println(c1 == c2)  // false — they are no longer equal because of mutable state
}
```

```kotlin
// IDIOMATIC — use immutable val properties and copy() to "modify"
data class Counter(val count: Int) {
    fun increment() = copy(count = count + 1)
}

fun main() {
    val c1 = Counter(5)
    val c2 = c1.increment()
    println(c1)  // Counter(count=5) — original unchanged
    println(c2)  // Counter(count=6) — new instance
}
```

`data class` is designed for **immutable** value holders. When you use `var` properties, you break the assumptions of `equals`, `hashCode`, and `copy` — they no longer reflect a stable "value". The idiomatic pattern is to use `val` properties and the `copy()` method to produce a new instance with updated values. This is the same pattern as Rust's `mut`/immutable-by-default design. If you find yourself wanting to mutate a data class's properties in place, ask whether you actually want a regular `class` (with `var` and identity-based equality) instead.

## Summary

- Kotlin classes are concise: `class Person(val name: String, val age: Int)` declares a class with two properties in one line. No `new` keyword — call the constructor like a function.
- Properties are unified with fields: `val`/`var` in the constructor parameters auto-generate getters (and setters for `var`). Custom getters/setters via `get()`/`set(value)` blocks.
- **Primary constructor** lives in the class header. **Secondary constructors** use `constructor(...)` and must delegate to the primary via `: this(...)`. **`init` blocks** run setup logic.
- Visibility: `public` (default), `private`, `protected`, `internal` (visible in same module). No package-private.
- Classes are **final by default** — mark with `open` to allow inheritance. Methods are also final by default; `open fun` allows `override fun`. `override` is mandatory.
- **Interfaces** can have abstract methods AND default implementations. A class can implement multiple interfaces.
- **`data class`** auto-generates `equals`, `hashCode`, `toString`, `copy`, and `componentN` (destructuring). Use for DTOs and immutable value holders. Properties should usually be `val`.
- **`sealed class`** restricts subclasses to the same file/package. Enables exhaustive `when` matching — the compiler errors if you forget a case. Kotlin's equivalent of Rust enums.
- **`object`** declares a singleton in one line. **`companion object`** inside a class holds static-like members accessed via the class name. No `static` keyword in Kotlin.
- Arrays use reference equality with `==` — use `.contentEquals()` or prefer `List<T>` instead.

You now understand Kotlin's object-oriented side, including the killer features `data class` and `sealed class`.
